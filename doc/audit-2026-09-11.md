### P1 — 本迭代修复（6 项）

#### `ROB-01` `Zhihu.js` 缺少顶层 `try/catch` → `$done()` 永不回调，请求悬挂

- **位置**：`src/Zhihu.ts:33-39`（`try/catch` 仅包住 `JSON.parse`）；处理链 `52-188` 行**完全无保护**
- **证据（已实测复现）**：用仓库自带 `test/harness.js` 构造 `topstory/recommend` 且 `body.data` 为**对象**（非数组）的响应：
  ```
  [Zhihu] doneCalls = []          ← $done 从未被调用
  [Zhihu] logs = ["知乎 - 推荐列表"]
  ```
  `body.data.filter(...)` 抛 `TypeError`，无 `try/catch` 捕获，脚本直接终止。
- **影响**：在 Loon 中，脚本未回调 `$done` 意味着**请求挂起到宿主超时**。用户侧表现为"知乎偶发加载失败/长时间转圈"，且**无任何日志**可归因。这是本次审计中唯一一个"用户可感知 + 静默"的缺陷。
- **建议**：与 `src/Keep.ts`、`src/Ximalaya.ts`、`src/Weibo.ts` 的三段式对齐——顶层 `try { 全部处理逻辑 } catch (e) { log(e); $done({}); }`；并补一条"`data` 非数组"的回归用例。

#### `BUG-01` `/ad/i` 子串匹配造成功能性误杀（Kugou / Youku / AlipayMini）

- **位置**：`src/Kugou.ts:17`（`Array.isArray(o[k]) && /ad/i.test(k)`）、`src/Youku.ts:41`、`src/AlipayMini.ts:156`（`key.toLowerCase().includes(keyword)`，`adKeywords` 含 `'ad'`）
- **证据（已实测复现）**：
  ```
  输入 {"header":["keep-me"],"ads":[{"a":1}],"loading":[1,2,3]}
  Kugou 输出 {"header":[],"ads":[],"loading":[]}
  Youku 输出 {"header":[],"adList":[],"loading":[]}
  ```
- **影响**：`header`(he**ad**er)、`loading`(lo**ad**ing)、`download`、`upload`、`badge`、`thread`、`gradient`、`read`、`cascade`、`upgrade`、`broadcast` 等键**均含子串 "ad"**，其下的数组会被清空、对象会被删除。这类键在真实 App 响应中极其常见（分页游标、列表容器、状态字段），会造成接口数据缺失——**用户侧表现为功能异常而非"广告没去掉"**，是最难归因的一类缺陷。
- **建议**：改为词边界匹配，例如 `/(^|[_.-])ads?([_.-]|$)/i`，或直接使用显式键名集合（`ad`/`ads`/`ad_list`/`adList`/`adinfo`/`ad_data`）；对每个脚本补一条"合法键不被误杀"的回归用例（本次的 `header`/`loading` 输入即可直接作为用例）。

#### `BUG-02` `Feishu` 的 `\b(ad|promot|sponsor|banner)` 词首匹配误杀 `adaptive`

- **位置**：`src/Feishu.ts:9`
- **证据（已实测复现）**：
  ```
  输入 items = [{type:"adaptive",v:1},{type:"ad",v:2}]
  Feishu 输出 {"items":[]}      ← 两条都被删除，adaptive 属误杀
  ```
  `\b` 是**词边界**而非词尾边界，`"adaptive"` 在位置 0 满足 `\b` 且以 `ad` 开头，因此命中。
- **影响**：同类误杀面覆盖 `adaptive`、`advertisement`（真广告，正确）、`adobe`、`admin`、`adult`、`addon`、`address` 等所有以 `ad` 开头的类型名。`admin`/`address` 类字段在飞书（协作办公产品）的响应中出现概率不低。
- **建议**：改为 `^(ad|advert|promot|sponsor|banner)(s|_|$)`，或与 `AD_KEYS` 一样改为枚举比对。

#### `SEC-02` DualSubs 5 条 script-path 走 GitHub `latest`，镜像哈希门禁覆盖不到载荷

### 3.2 架构设计合理性 —— 优秀（A-）

**三条产物链，每条都有正反向门禁**，这是本项目最强的架构特征：

```
src/*.ts ──esbuild──▶ Scripts/*.js          （漂移门禁: git diff）
template/loon.tpl + snippet ──surgio──▶ Profile/Loon.lcf   （tpl-sync-check 正反向行集合）
Mirror/ ──mirror-scripts──▶ Mirror/MANIFEST.json           （sha256 + config-validate 8b 一致性）
```

**其他架构亮点**
- **分层隔离清晰**：`Plugin/`（自维护）vs `Kelee/`（上游外壳）vs `Mirror/`（镜像），三者规则边界明确，`plugin-lint-check` 与 `mitm-orphan-check` 分别覆盖。
- **门禁哲学一致**：多处采用"上游失活即保留旧版 + fail-red"（geonode `MIN_NODES`、startup 插件 `<50 条`、mirror `keep_old`），而非"失败即清空"。这是正确的取舍方向。
- **最小权限原则落地**：`[MitM]` 有 49 条银行负向排除 + 55 条正包含；`mitm-orphan-check` 强制"每个解密域必须被规则消费"，避免纯解密扩张证书暴露面。974 个 hostname 全部通过。
- **凭据零入仓**：`surgio-build.yml` 的凭据断言（`grep -niE '(^|,) *(password|uuid|bob|encryption) *='`）已针对大小写与等号旁空格加固；本次全仓 secrets 扫描**零命中**。

**架构张力点**
- **`Profile/Loon.lcf` 的真源身份模糊**（`ARCH-01`）：名义"生成物"、实为"手维护 + 事后比对"。本次实测证明生成链**完全可复现**，因此当前状态是"两者都是真源"——这是最脆的组合。建议立即升级为强门禁（generate + git diff）。
- **`[Remote Rule]`/`[Plugin]` 的引用目标跨三个分发面**（CDN / S3 / GitHub 直连），新鲜度与信任等级不等（`DATA-01`、`SEC-02`）。
- `provider/tokyo.js` 与 `surgio.conf.js` 双份 provider 定义（`CODE-04`）。

### 3.3 安全漏洞 —— 良好（B），1 项 P0

| `Scripts/Qidian.js` | 601,793 B 单文件 | ⚠️ 见下 |

**问题项**
- `PERF-01`：goodbyeads 115,076 条规则的匹配成本（**净新增 115,054 条，不冗余**，需实测客户端开销）。
- `Scripts/Qidian.js` 601 KB：体积本身非瓶颈（cron + 少量请求触发），真正问题是**不可审计**（`ENGINE-MANIFEST.json` 的 `known_risks` 已如实记录"静态不可审计，等价于信任不公布源码的第三方，拥有 `$httpClient` 与全部持久化权限"）。**值得肯定的是**：manifest 还记录了"每次 cron 签到与每次 `getlogininfo` 抓包都会执行引擎 eval"，以及"Cookie 更新时 notify 正文包含完整 cmfuToken（锁屏可见）"——这类自我披露在同类项目中极为罕见。建议：不改代码，但考虑把"每次抓包都 eval"优化为按需触发。
- `Profile/geonode.loon.txt`：16 个免费代理（含 1 个 `http` 协议节点）。注意 `tools/geonode-sync.mjs:11-13` 的注释称"http 协议全部失败（不支持 CONNECT 隧道）"，而实测有 1 个 http 节点通过探测——说明**注释已陈旧**，或探测偏宽松（见下）。

**一处探测宽松性观察**：`tools/geonode-sync.mjs:59-62` 的 `OK_STATUS` 包含 3xx（`301/302/307/308`），理由是"证明 CONNECT/转发链路完整"。该理由成立（目标站自身重定向确实说明链路通），但**误判代价非零**：免费代理返回"重定向到拦截页"也会被计入可用，而误判的后果是用户 `OpenCode` 组静默走不通。建议：探测加 `-L` 跟随并校验**最终**状态码为 2xx，或额外校验响应体不含代理错误页特征。

### 3.5 依赖项版本与兼容性风险 —— 良好（B+）

**优点**
- **三个 devDependencies 全部精确固定**（`esbuild: 0.28.2`、`eslint: 10.9.1`、`surgio: 3.19.0`，**无 caret**），配合已提交的 `package-lock.json`（355 KB）与 CI `npm ci`，构建完全可复现。这是**有意的正确取舍**。
- **零运行时依赖**（`package.json` 无 `dependencies`），分发产物不含任何第三方代码。
- `dependabot.yml` 的 `ignore` 块有**逐条理由注释**（含 issue/run 编号），不是无脑屏蔽。
- `surgio.conf.js` 的 provider 在无 `SURGIO_SUBSCRIPTION_URL` 时降级为 `{ type: 'custom', nodeList: [] }`，使 CI 无需凭据即可构建。

**风险项**
- `DEP-01`：43 条漏洞（复核结论：可接受，见详述）。
- `DEP-02`：无 `engines` 字段。
- `DEP-03`：无类型检查，盲区已被 `CODE-03` 实证。
- `ENV-01`：本机默认镜像源不支持 `npm audit`。
- **上游兼容性**：`kelee.one` 自 2026-08-25 起全局 403（含浏览器 UA），对应 `upstream-health` issue #27。项目已妥善降级（本地 `Kelee/Google.plugin` 替代 LPX，其余 6 个 LPX 无本地替代已移除）。**剩余风险**：`Kelee/*.plugin` 15 个外壳的可用性**无法从 CI 验证**——`upstream-health.yml:35-37` 把 kelee.one 的 403 视为"健康"，这个白名单逻辑本身合理（Loon 带 Turnstile 可拉取），但长期 403 会**永久白名单化**，掩盖真实的持续不可用。建议对该 URL 增加"连续 N 天 403"计数并在超阈值时告警。

### 3.6 错误处理与边界条件健壮性 —— 中等（C+），**本次审计的最大短板**

**优秀样板（可作为全仓模板）**
- `src/Umetrip.ts`：protobuf wire 级解析器有全面的边界检查（`readVarint` 的 `shift <= 56` 溢出保护、`parseMessage` 对 `wire` 合法性/长度越界的逐项返回 `null`）、递归深度上限 `depth > 12`（出现在 `removeMatchingNodes`/`rewriteJsonFields`/`cleanFamilyMessage`/`rewriteMineJsonFields` **四处**）、`bytesToUtf8` 的截断保护、入口 `$response && $response.bodyBytes` 双重守卫。这是全仓工程质量最高的文件。
- `src/Luckin.ts`：内联 AES-128 实现，`decryptBody` 有密文长度非 16 倍数检查 + PKCS7 填充合法性校验；`main()` 整体包在 try/catch 中，catch 内**回退到原始 body**（而非空体）——正确的降级方向。
- `src/AlipayMini.ts:82`：`(async()=>{...})().catch(e => { log(e); $done(); })` —— 顶层兜底 + 兜底内必调 `$done`，是正确形态。
- `src/Keep.ts` / `src/Ximalaya.ts` / `src/Weibo.ts`：统一的三段式（运行时守卫 → 顶层 try/catch → catch 内 `$done`）。

**问题项**
- `ROB-01`（P1）：`Zhihu.ts` 无顶层 try/catch，**已实测复现 `$done` 永不回调**。
- `BUG-01` / `BUG-02`（P1）：键名匹配过宽导致功能性误杀，**均已实测复现**。
- `ROB-02`（P2）：`Bilibili.ts` 的 `run()` 无 `.catch()`。
- `TEST-01`（P2）：harness 无法检测"未调用 `$done`"，是 `ROB-01` 逃逸的直接原因。
- **边界守卫质量参差**：
  - `src/Zhihu.ts:197`：`Object.fromEntries(url.split("&").map(p => p.split("=")))` —— 遇 `videoID=a=b` 会截断值（`split("=")` 无 limit）。应改用 `URLSearchParams`。
  - `src/Luckin.ts:197`：`MYPAGE_BLOCK[item && item.title as string]` —— 用对象字面量做查表，`title === "constructor"` 会命中原型链返回真值（误过滤）。应改用 `Object.create(null)` 或 `Map`。同型模式见 `src/Weibo.ts:371`（`itemMenusConfig[type]`）。
- **`$done()` 语义不统一**：`env.ts:21` 的 `$.done()` 默认传 `{}`；`Douyin.ts:84`、`Fanqie.ts:30`、`Kugou.ts:12`、`Youku.ts:27` 直接调全局 `$done()`（传 `undefined`）；`Keep.ts`/`Ximalaya.ts` 用 `$done({})`。三种写法在 Loon 中语义可能不同（`$done({})` = 不修改，`$done()` = ？）。建议统一为 `$done({})`。
- **`$response.body` 守卫不统一**：`Kugou.ts`/`Youku.ts`/`Dianping.ts`/`Meituan.ts`/`WPS.ts` 只守卫 `$response` 存在，未守卫 `$response.body` 非空；`Douyin.ts`/`Fanqie.ts`/`Feishu.ts`/`Kuaishou.ts` 两者都守卫。建议统一。

**测试覆盖评估**
- **接线覆盖满分**：108 个用例引用了全部 **27** 个 `Scripts/*.js`（实测 27/27，无遗漏），配合 `wiring-check.js` 的双向校验。
- **行为覆盖偏科**：用例高度集中在 `Weibo`/`Luckin`/`Umetrip`/`Qidian` 等复杂脚本；`Kuwo`/`WPS`/`Youku`/`Kugou` 等简单脚本仅 1–2 条。**本次确认的 3 个缺陷（`ROB-01`/`BUG-01`/`BUG-02`）全部落在用例稀薄的脚本上，且无一有对应用例**——这不是巧合。
- **建议**：按"每个 handler 至少一条异常输入用例"补齐四类：① 非数组/非对象结构；② `null`/缺失 body；③ 非 JSON（HTML/protobuf）；④ 深嵌套（>12 层，验证深度上限）。

| 维度 | 评级 | 一句话结论 |
|---|---|---|
| 代码质量与规范性 | **B+** | 注释与结构规范优秀；缺共享模块层已造成实际重复缺陷 |

按本报告的四批路线图推进，可在不破坏现有工程优势的前提下，把"错误处理"维度从 C+ 提升到 A-。
