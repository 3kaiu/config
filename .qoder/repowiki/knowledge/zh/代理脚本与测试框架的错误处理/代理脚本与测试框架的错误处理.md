该仓库是一个基于 Surgio 的多客户端代理配置生成工程，主要面向 Loon、Quantumult X、Surge 三个 iOS 代理客户端。在错误处理方面，代码库呈现出以下特点：

**1. 运行时错误处理模式**
- 代理脚本（Scripts/ 目录）采用 try-catch 包裹关键网络请求和 JSON 解析操作，失败时原样返回原始数据，确保代理流程不被中断
- 使用 $done() 回调作为统一出口，无论成功或失败都通过该函数返回结果，保证客户端能正确处理响应
- 对非法 JSON、非 JSON 格式（如 Proto）等异常情况采用"原样放行"策略，避免破坏正常业务逻辑

**2. 测试框架的错误处理机制**
- 自定义测试运行器 `test/run-tests.js` 实现了零依赖的测试执行环境，通过 try-catch 捕获每个测试用例的执行异常
- 测试断言系统使用 `assert.fails` 数组收集失败信息，最后统一抛出 Error 对象，便于 CI 管道识别失败原因
- 沙箱环境 `test/harness.js` 模拟 Loon/QX 运行时，对未处理的 Promise 拒绝进行静默处理（`.catch(() => {})`），避免测试被意外中断

**3. 镜像规则的错误恢复**
- `Mirror/rules/qx-resource-parser.js` 包含大量 try-catch 块，针对网络重试、UA 切换、内容解析等场景实现容错
- 支持 UA 重试机制，当检测到特定错误时自动切换到备用 User-Agent 重新获取资源
- 错误分类通过 `Perror` 变量标记不同错误类型，实现细粒度的错误处理策略

**4. CI/CD 层面的错误处理**
- GitHub Actions 工作流中使用 `if ! curl ...; then` 模式处理网络请求失败，配合 `--retry` 参数实现自动重试
- CDN 验证和镜像脚本下载失败时记录详细错误信息并继续执行其他任务，保证流水线鲁棒性

**5. 开发规范约束**
- ESLint 配置中将 `Error` 和 `TypeError` 设为只读，防止意外覆盖全局错误类型
- 测试用例通过明确的断言消息描述期望行为，便于快速定位问题

整体而言，该项目的错误处理遵循"防御性编程"原则，在网络请求、数据解析、脚本执行等关键环节都设置了适当的容错机制，确保代理服务的稳定性和可用性。
